# Hyperparameter Sweep — learning rate × entropy target

**Task:** Day 22 (Master Plan v3) — sweep the two knobs most tied to the observed
failure modes on the demo-seeded trainer, and check whether the current defaults
sit in a good region.

**Source of all numbers:** `runs/sweep_lr*/history.json` and `run_config.json`
(9 runs, generated by `sac/sweep.py`). Counts below were recomputed directly from
`history.json`, not read from a summary field — see Limitations (2).

---

## What was swept

| axis | values |
|---|---|
| `--lr` | 1e-4, 3e-4, 1e-3 |
| `--entropy-target` | -1.0, -2.0, -4.0 |

Full 3 × 3 grid, one run per cell. Fixed for every run: demo-seeded trainer
(`--demos 12`), `--curriculum none`, seed 42, `--steps-scale 0.1` (20k steps),
`--eval-every 2000` → 10 target evals per run.

An eval counts as **solved** iff `target_eval.completed == true` **and**
`target_eval.crashed == false`.

## Verdict

**lr dominates; entropy target does not matter here.**

- `lr=1e-4` solves ~5× slower — step 10000 vs step 2000 — and holds the solve for
  only 6/10 evals vs 10/10. This is consistent across all three entropy values.
- `lr=3e-4` and `lr=1e-3` both solve fast (step 2000) and stably (10/10, except
  1e-3/-4.0 at 9/10). Nothing separates them.
- `entropy_target` has negligible effect at every lr. Expected: demo-seeding
  already supplies the exploration that the entropy term would otherwise have to
  produce, so the knob has little left to do.
- No config showed instability — no run solved and then lost the lap permanently,
  and every run finished with `completed_run: true`.

**Current defaults are confirmed to be in the good region.** `sac/agent.py:12,39`
defaults to `lr=3e-4` and `target_entropy=-action_dim` = **-2.0**, which is the
3e-4 / -2.0 cell: solves at step 2000, 10/10 evals. No change recommended.

---

## Limitations

**(1) Single seed — the lap-time column does not rank the top configs.**
Every run used seed 42. Within a *single* run, lap time varies by 5-22 steps
across its own evals (e.g. 3e-4/-1.0 ranges 388→404 over 10 evals). The spread
between config best-laps (382-402) is smaller than the spread inside several
individual runs, so differences like 392 vs 397 are run-to-run noise, not a
ranking. Note that the fastest single lap (382) belongs to the *least* stable of
the fast configs (9/10, solved at 4000) — picking on best-lap rewards variance.
Only the large `lr=1e-4` effect (5× slower solve, 6/10 vs 10/10, consistent
across all three entropy values) is trustworthy from single-seed data. Ranking
the top five configs would need multiple seeds per cell.

**(2) The sweep script initially misreported "No config solved stably."**
`sac/sweep.py` read `n_solved_evals` from each run's `run_config.json`, but
`sac/train_curriculum.py` never writes that field, so it defaulted to 0 for all 9
runs and every config failed the "stable" gate. The training runs themselves were
fine. Fixed to count solved evals from `history.json` directly; the corrected
counts match an independent hand count on all 9 runs. The stale
`runs/sweep_results.json` from the buggy run is self-contradicting
(`solved_at: 2000` alongside `n_solved_evals: 0`) and should be regenerated.

Two smaller recording gaps remain, neither affecting the numbers above:
`run_config.json` does not record `lr` or `target_entropy` (they were recovered
from run directory names), and `sweep.py`'s `lap_time` column reports the *first*
solved eval's lap rather than the best (401 vs 382 for 1e-3/-4.0).
